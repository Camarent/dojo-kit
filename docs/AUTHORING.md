# Authoring reference

Reference rules for the AI model that generates a course from a user's materials. The procedure (order of steps, commands, turn-limit rules) is in `AGENTS.md`; this file holds the field lists and content rules. Item fields and validator codes: `./dojo schema --brief` (lists the main fields; `schema/course.schema.json` is the complete reference). Real shapes: `examples/showcase/` and `examples/demo/`.

## Files of a course
`workspace/<course-id>/`:
- `course.json` - id, title, uiLanguage, contentLanguage, units, optional exam(s) and settings.
- `content/<unit-id>.jsonl` - generated by `./dojo add`; one JSON object per line.
- `materials/` - the user's sources. `MAP.md` - plan, one line per unit. `GAPS.md` - what no item type could express.
- `ids.lock` - written by `./dojo lock` / `./dojo build`.
- `stimuli.jsonl` - optional shared passages (see "Shared passage").

## Item types and fields
Common: `type`, `prompt` (required); optional `tags`, `explanation`, `source`, `status` (`active`|`retired`), `stimulus`, `supersedes` (see "Superseding retired items"); `id` and `unit` are filled by `./dojo add`. Unknown fields are rejected. Ids match `^[a-z][a-z0-9]*-[0-9]+$`.

| type | required | optional | notes |
|---|---|---|---|
| `choice` | `options` (2+; use 3-5), `answer` (0-based index) | | true/false is `["True","False"]`; the app shuffles options |
| `multi` | `options` (3+), `correct` (indices, non-empty, fewer than options) | | prompt says several answers are right |
| `gap` | `answers` (all accepted forms) | `retry`, `normalize` | `retry` = readings that are close but not correct; must differ from `answers` |
| `cloze` | `parts`: strings (text) and arrays of strings (blank + alternatives) | `normalize` | 1-5 blanks (more warns, over 10 errors) |
| `numeric` | `answer` | `tolerance` (absolute), `unitLabel` (display) | |
| `match` | `pairs` `[{left,right}]` (2-6; 2-8 allowed) | `distractors` | lefts distinct, rights (and distractors) distinct |
| `order` | `steps` in correct order (3-7; 2-10 allowed) | | the app shuffles; with one `___` per step the words are tapped into the sentence; without `___` they are listed |
| `card` | `back` (front is `prompt`) | | self-rated; never in an exam |

Example shapes (from `examples/showcase/content/shapes.jsonl`):
```
{"type":"choice","prompt":"How many sides does a hexagon have?","options":["5","6","7","8"],"answer":1,"explanation":"Hexa means six."}
{"type":"multi","prompt":"Select all shapes with four sides.","options":["Square","Triangle","Rectangle","Pentagon"],"correct":[0,2]}
{"type":"gap","prompt":"A right angle measures ___ degrees.","answers":["90","ninety"]}
{"type":"cloze","prompt":"Fill in the blanks","parts":["A triangle has ",["3","three"]," sides."]}
```
`normalize` (gap, cloze, or course-wide in `course.json`): `caseSensitive` (default false), `trim` (true), `collapseSpaces` (true), `stripPunctuation` (false), `fold` `[[from,to]]`.

## Adding items
```
./dojo add workspace/<course-id> <unit-id> <<'EOF'
[ {...}, {...} ]
EOF
```
Also `--file <path>` (read the batch from a file) and `--dry-run` (check without writing). All items are added or none; errors are printed as `item k: message`. 8-15 items per call. Never write `content/*.jsonl` by hand (AGENTS.md section 4a). `./dojo next-id workspace/<course-id> <prefix> --count N` prints N free ids (nothing is reserved).

## Unambiguous-answer rules
1. A learner who knows the fact must be able to answer without guessing; a gap has exactly one answer (every accepted spelling goes into `answers`; several different answers only when the prompt says "any" or "one of").
2. The prompt matches the input type: no "write" on choice/match/order/card, no "choose/pick" on gap (validator `prompt_type_mismatch`); no two non-stimulus gap/cloze/numeric items share the same normalized prompt with different normalized answer sets (validator `same_prompt_different_answers`).
3. Options are unique after normalization (`choice_duplicate_options`, `multi_duplicate_options`); no readings glued with "/" in options (`ambiguous_answer`). Slashes inside a parenthetical note are fine. Alternatives like "брат/сестра" must be split into separate options or written with "or".
4. The answer is not in the prompt (`answer_in_prompt`; for a listening script the question may name the topic, never the answer).
5. The right option is not the longest; distractors have similar length and form and are mistakes a real learner makes. No "all/none of the above".
6. Each item stands alone: the learner sees one item at a time.
7. The number of `___` in an `order` prompt equals the number of steps (`order_blanks_mismatch`).
8. Text uses only Latin, Cyrillic, Hiragana, Katakana, CJK (plus punctuation and digits); other scripts need `"scripts": ["Arabic"]` in `course.json` (`foreign_script`).
9. No source answer, no item: if the material does not give the answer, leave the item out.

### Shared passage (reading, dialogue)
Per AGENTS.md section 4a: put the full text into the `prompt` of every item that needs it, one question per item; never drop the answer-bearing text to save space. The format also has a `stimulus` field referencing an entry of `stimuli.jsonl` (`id`, `text`, optional `title`, `hideText`, `speak`); an exam draws the items of one stimulus together. Use it only when the user asks for it; validator codes `unknown_stimulus`, `duplicate_stimulus`, `stimulus_group_split` apply. Record anything else that no type can express (audio, markup, timers) in `GAPS.md`.

## Content self-check
Before `./dojo build`:
- [ ] `./dojo validate workspace/<course-id> --json` exits 0; every warning read and fixed or justified (a `prompt_too_long` warning on a prompt that carries a full reading passage is accepted).
- [ ] Each `choice` has exactly one defensible right option; each `multi` has all and only the right ones.
- [ ] Each gap/cloze blank has all accepted spellings and no answer that is also a wrong answer.
- [ ] Prompt/type match, no leaked answer, no longest-option tell, options unique.
- [ ] Every fact is supported by the materials; `source` names file and section; explanations are true.
- [ ] Units cover the materials proportionally (`./dojo stats workspace/<course-id>`); types are mixed.
- [ ] Review a random 10-15% as a learner; fix or retire the bad ones.
- [ ] `GAPS.md` lists what could not be expressed; the user is told which items were left out and why.

## Ids and ids.lock
- Ids are permanent: never reuse, renumber or delete. Remove an item with `"status":"retired"`.
- Changing an item's type or correct answer = retire it and add a new item (progress belongs to the id). Wording and typo fixes keep the id.
- `./dojo lock workspace/<course-id>` records ids in `ids.lock` (refuses on errors); `./dojo build` updates it too.
- Validator guards: `id_removed` (locked id missing), `retired_id_reused`, `item_type_changed`, `duplicate_id`.

## Units and per-unit settings
`course.json` `units`: `[{id, title, ...}]` (id `^[a-z0-9][a-z0-9_-]{0,47}$`; aim for 10-40 items per unit; drop empty units). Unit-level optional fields:
- `newPerDay` (integer >= 0) - cap on new items per day for that unit.
- `srs` - `{ladder, dropOnWrong}` for that unit.
- `placement` (bool) - `false` excludes the unit from the placement test (needs course-level `placement`, else `placement_unused`).
- `newOrder` - `"file"` or `"random"`: order in which new items appear.
- `examOnly` (bool, default false): exam sections draw this unit's items first, fill up from shared units; training prefers shared items and uses these only if the queue would be empty (`crates/dojo-core/src/exam/`); see "Exams".

Course-level counterparts and extras: `srs`, `srsByType` (per item type), `newOrder`, `learnedStage`, `types` (restrict item types), `introNew`, `dontKnow`, `allowOverride`, `normalize`, `speech`, `scripts`, `captions`, `ruby` (see "Question captions and ruby skip set").
- `srs.ladder`: intervals in milliseconds by stage; at least 2 entries, first 0, non-negative, non-decreasing. Default `[0, 14400000, 86400000, 259200000, 604800000, 1209600000, 2592000000]`. Leave it alone unless the user asks (e.g. an exam date soon).
- `srs.dropOnWrong`: stages lost on a wrong answer, integer 0-10, default 1.
- `learnedStage` (integer >= 1): stage at which an item counts as learned; default 4 in the web app (`web/session.js`), capped by the length of the unit's ladder.

## Placement test
Course-level `placement`: `{"perUnit": 5, "mode": "check"}`. `perUnit` = items sampled per unit (default 5, minimum 1). `mode` defaults to `check` (cards skipped, types mixed, units interleaved); the web app also has a `self` mode. Exclude units with unit-level `placement:false`.

## Exams
Single exam: `exam: {minutes?, passMark?, pass?, sections: [{title, count, units?, tags?, types?}]}`. Take the real exam's format and pass rule from the user; do not invent them. A section's `count` must not exceed the matching active items (`exam_too_big` warning); a section cannot use `card` or a type not enabled (`bad_exam_section`).
Several exams: `exams: [{id (required, unique, frozen once published), title?, minutes?, passMark?, pass?, sections, timing?, scoring?, passPoints?, note?}]`; the legacy `exam` has id `default`.
Pass rule:
- `passMark` is optional: a fraction 0..1 (0.7 = 70%); pass when correct/total `>=` it. Absent, the default is 0.6 (`DEFAULT_PASS_MARK`, `crates/dojo-core/src/exam/`). `pass_rule_default` warns when none of `passMark`, `pass` or `scoring` is set: confirm the rule with the user.
- `pass: {mode?: percent|points, basis?: official|author, source?, scaled?}`. `mode` defaults to `points` when `scoring` is set, else `percent` (`crates/dojo-core/src/exam/`). In points mode `passMark` is ignored (`pass_mark_ignored` warning); `mode: points` without `scoring` is an error (`bad_pass_rule`). `basis: official` without `source` warns (`pass_rule_no_source`). `scaled: true` sets the result's `estimate` flag, points mode only (`crates/dojo-core/src/exam/`).
Exam-only questions (soft rule: warnings only, never blocks `dojo validate`):
- Ideally mock-exam questions differ from training questions: put them in units with `examOnly: true` (unit field above) and point the exam sections at those units.
- Each exam section needs at least 20% of its `count` (rounded up) from `examOnly` units; below that `exam_few_unique` warns (`crates/dojo-core/src/validate/exam.rs:279`).
- Decide the split once the materials are known (e.g. past papers or chapter tests kept for the exam only); ask the user if unclear. If materials are scarce, overlap is allowed: accept the warning and mention it in the final report.
- `timing: [{sections:[section titles], minutes}]` - timer groups; a section is in at most one group.
- `scoring: [{title, sections:[...], points, minPoints?}]` - score parts; `passPoints` = points needed to pass. Section titles must be unique (`unknown_section`, `bad_exam`).

## Plugins and markup
`course.json`: `"plugins": {"scripts": ["x.js"], "styles": ["x.css"]}` and `"markup": "<plugin-name>"`. Plugin paths are relative to the course folder, no `..`, no absolute paths (`bad_plugin_path`); files are inlined at build time. Example: `examples/plugins/ja-readings/` (README there) renders `{漢字|よみ}` as ruby with display modes kana/romaji/none; it needs `"markup": "ja-readings"` or it does nothing. For readings in choice/multi options use separate options, never "a/b" (rule 3). Built-in, no plugin needed: `"markup": "ruby"` for `{base|reading}` annotations (furigana, pinyin, any gloss), `speech.voices.<role>.prefer` (voice-name regexes), `inputScript` (see CONTRACT section 4). Use plugins only when the user asks.

## UI and content languages
`uiLanguage` (`en` and `ru` are shipped) and `contentLanguage`. For another UI language the course supplies `i18n/<lang>.json` next to `course.json`, with the keys of `web/i18n/en.json` (AGENTS.md section 9); `dojo build` overlays it on the shipped file key by key, and a missing language falls back to en with a warning. Ru plural forms are `.one`, `.few`, `.many`, `.other`; other languages use `.one` and `.other` only. Items are written in the content language; do not mix in other scripts.

Keys starting with `plugin.` or `course.` in `i18n/<lang>.json` are reserved for plugins and the course and are never reported as unknown.

## Course tests
Course tests that need the framework find it with `tools/fw-root.js`; set `DOJO_KIT_ROOT=<dojo-kit dir>` when the course is not nested inside the framework tree.

## Question captions and ruby skip set
- `captions` (course-level): object `key -> text`. The key is an item tag or an item type (`choice`, `multi`, `gap`, `cloze`, `numeric`, `match`, `order`, `card`). For a question, the first of the item's tags with an entry wins, then the entry for its type, then the built-in caption for the type (`session.caption.<type>` in `web/i18n/`). An empty text shows no caption.
  ```json
  "captions": { "listen": "Listen, then answer", "choice": "Pick one" }
  ```
- `ruby` (course-level): `{"skip": "<text>", "skipTag": "<tag>", "skipKey": "meta.kanji"}`, all keys optional. Applies to the built-in `ruby` markup (`"markup": "ruby"`) only.
  - The skip set is the Han characters (kanji) of `skip`, plus those of the string at item path `skipKey` (default `meta.kanji`) of every item tagged `skipTag`.
  - `{base|reading}` whose base characters are all in the set shows only the base. A base with any other kanji keeps its reading.
  - Only the displayed ruby changes. Speech, search and plain text never include readings.
  ```json
  "ruby": { "skipTag": "core", "skipKey": "meta.kanji" }
  ```
- `dictKeys`: dotted item paths holding `{w, r}` word-reading entries for the ruby dictionary (default `meta.examples`, `meta.irregular`; `web/ext/registry.js:166`); `skipKey` defaults to `meta.kanji`. Course `breakdown`: `{key, meaning, readings:[...]}` dotted paths into the item for the kanji breakdown. `speech.lang` picks the voice language.
- Core types both fields but does not validate them, so a wrong value is found only in the browser. Keys and paths are generic: they name your own tags and `meta` fields.

## Declarative detail rendering from item.meta
A course can declare detail fields to render from `item.meta` without a plugin. Add to `course.json`:
- Course-level: `"detail": {fields: [{key: "meta.<path>", label: "<label>", type: "text"|"list"|"objects", fields?: [...]}]}`
- Per-unit override: `units[].detail` with the same shape.

Field types:
- `text`: render as plain text (with course markup applied).
- `list`: render as `<ul>` with each element as a list item.
- `objects`: render as a table with rows of "key: value".
- `table`: value `{head: [..], rows: [[..],..], title?}` renders a table with header cells and an optional caption (`web/ui/detail.js:79`).
- `pairs`: value is a list of objects; two columns are read from `keys: [left, right]` (default `a`, `b`); entries missing either key are skipped (`web/ui/detail.js:96`). `keys` on any other type is `bad_detail_keys`.

Rules:
- `key` is a dot-separated path into `item.meta` (e.g., `"meta.meaning"`, `"meta.readings.kanji"`).
- Missing, empty, null, or undefined fields are skipped.
- Text is escaped; no innerHTML (HTML entities in the text are shown as text).
- Ruby markup and `renderText` are honored for string values.
- A registered plugin detail hook takes precedence over declarative detail.
- `labelKey` (i18n key) is used when `label` is absent; a leading `meta.` in `key` is optional.
- Unknown `type` values (anything but text, list, objects, table, pairs) are a validation error (`unknown_detail_type`).
- Course-level `detail.glyph` (dotted path into the item, header glyph) must not be empty (`empty_detail_glyph`).

Example:
```json
{
  "detail": {
    "fields": [
      { "key": "meta.meaning", "label": "Meaning" },
      { "key": "meta.readings", "label": "Readings", "type": "list" },
      { "key": "meta.info", "label": "Info", "type": "objects" }
    ]
  }
}
```

This renders for items with `meta: {meaning: "test", readings: ["a", "b"], info: {level: "N5"}}` as:
- Meaning: test
- Readings: (as unordered list)
- Info: (as table with row "level: N5")

## Copyright
Write your own questions and short explanations. Quote at most a short phrase. No long passages, full tables or whole exercises. `source` points to file and page/section; it does not copy.

## When to leave an item out
Leave the item out and tell the user when: the materials give no answer or two readings are defensible; the page is unreadable (bad OCR); the fact needs an unavailable audio/image; the right answer cannot be made unique in the available type; the source is the only wording and would need a long quote. List these in the final report (and in `GAPS.md` when it is a format limit).

## Superseding retired items
When a retired item is replaced by a new one, list the retired ids on the live item: `"supersedes": ["old-1", "old-2"]` (optional, any item type). Learners' saved progress is then carried over automatically at load; no document marker is written.
- Validator error `bad_supersedes`: field on a retired item, empty list, duplicate id, the item itself, an id that is not retired, or an id listed by two successors. For a chain, list all transitive predecessors.
- Fold rule (`crates/dojo-core/src/migrate.rs:44` `migrate_progress`): the successor is folded only if some predecessor has a record and the successor has none or an older `last`. Result: `s` and `due` = min, `ok` and `bad` = max, `last` = max over successor and predecessors (predecessors with `last` before `resetAt` are ignored). Retired records are never changed. Re-running is a no-op, so it is idempotent.
- Content using `supersedes` needs a framework build that knows the field (unknown fields are rejected).

## Legacy progress import

To import progress from an old format (pre-v1), use:
```
./dojo import-progress <old.json> --map <id-map.json> --course <course-dir> [--out <file>] [--write] [--now <timestamp>]
```

Old format: `{items: {<oldId>: {s, due, ok, bad, last}}, stats: {days, newByDay}, settings}`.

The id-map maps old IDs to new IDs: `{"oldId": ["newId", ...]}` or `{"aggregate": "min|mean|max|first", "ladderLen": N, "map": {...}}`. When multiple old records map to the same new ID, they are aggregated. Stages are clamped to the ladder length. Only `newPerDay` and `placementDone` from settings are passed through. `stats.days` and `stats.newByDay` are preserved. Unknown old IDs are reported.

Dry-run is the default (prints report, writes nothing). Use `--write` or `--out` to write the file.

If the course has `srs.scope = "entity"`, after import identical records are written to all members of each entity (min stage, max ok, max bad) so topics land consistent.
