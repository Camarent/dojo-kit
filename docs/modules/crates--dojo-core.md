# crates/dojo-core

`learnedStage` (course.json, integer >= 1) is typed here and validated (`bad_learned_stage`); core reads it in the groups logic: `group_counts` (`crates/dojo-core/src/groups.rs`) applies `DEFAULT_LEARNED_STAGE` = 4 when unset; `entity_stats` takes the stage as a parameter. The browser clamps the unit threshold to the unit ladder's last index in `web/session/overrides.js` (`getUnitThreshold`).

## Purpose
Library crate holding every decision that must be correct: what an answer grades to, when an item is due, how two progress documents merge, how an exam is sampled and scored, and which course/content problems are reported. It has no clock and no I/O; callers pass `now` and `seed` in. Shared by `dojo-cli` (native) and `dojo-wasm` (browser).

## Invariants and gotchas
- No clock, no randomness, no I/O in this crate: `now`, `seed`, timezone offset are arguments.
- `api::call` returns the merge refusal as a successful value `{"error":"course_mismatch"}` or `{"error":"invalid_document"}` (`crates/dojo-core/src/api.rs:122`-`:123`), not as an error envelope. JS callers must check for it.
- `gapVerdict` checks `answers` first: an input that matches an answer is `"ok"` even when it also matches a `retry` reading. `"retry"` only when no answer matches. `checkGap` ignores `retry`; the browser calls `gapVerdict` only for gap items that have `retry` readings.
- `retry` is typed on gap items only (`GapItem`, `crates/dojo-core/src/content.rs:303`); on another item type it is a parse error (`deny_unknown_fields`). A retry reading equal to an answer after normalization is `bad_retry` (error, `bad_retry` in `src/validate.rs`); an empty one is `gap_empty_answer`.
- `sanitize` of a non-object returns `null` through the API (`crates/dojo-core/src/api.rs:119`).
- `opts.fold` is checked in `normalize_opts` (`crates/dojo-core/src/api.rs:101`): a malformed entry makes the call return an error envelope; it is not ignored.
- Exam sampling (`crates/dojo-core/src/exam.rs:100`): candidates sharing a `stimulus` id are drawn as one group, whole and in input order; `count` counts items. A group larger than the remaining count is skipped (later groups may still fit). If a section is still short and some group has more than one item, a subset-sum pass (`reach` table in `sample`) picks the largest total <= `count`, and replaces the greedy picks only when it fills more. A `count` larger than the candidate pool is clamped to the pool size before the `reach` table is built (no allocation proportional to a huge `count`). The unfilled rest goes to `short` (`Shortage.short_by`); a section's `count` in `sections` is what was actually filled.
- Exam ids: `exams[]` entries need an id matching the course-id charset (`bad_id`), unique; the legacy `exam` must be id `default` or omitted, and it collides with an `exams[]` id `default` (`bad_exam`) (`check_course` in `src/validate.rs`).
- `timing` and `scoring` section titles must exist in the same exam's `sections` (`unknown_section`). Validator reports: `bad_exam` (0 minutes, empty group, 0 or negative points, `minPoints > points`, negative `passPoints`, a section in two timing groups or two scoring parts, empty `scoring[].sections`, timing group sections not consecutive in exam order).
- `compute_parts` (`crates/dojo-core/src/exam.rs:203`) errors, and the API returns an error envelope, when a part names an unknown section, a section is used by two parts, or a points value does not fit in u32 (`scoring[].points`/`minPoints` are range-checked in `api.rs` too). Part points are `round(points * raw / total)`; a part with total 0 scores 0.
- `score_with_parts` (`crates/dojo-core/src/exam.rs:241`): `pass` = fraction >= passMark (default 0.6 when absent) AND every part's `minPoints` met AND (when set) sum of part points >= `passPoints`. Without `scoring` the output is the plain `score` result (no `parts`).
- `stimulus_group_split` (warning, `check_stimulus_groups` at `crates/dojo-core/src/validate.rs:1000`): items sharing a stimulus differ in unit, tags, or type, or include a card.
- Stimulus validation: `stimuli.jsonl` line errors are `parse_error`; duplicate ids are `duplicate_stimulus`; an item whose `stimulus` is unknown is `unknown_stimulus` (code table `crates/dojo-core/src/validate.rs:41`). Items whose stimulus has `hideText: true` skip the leak check (`check_leak`, `crates/dojo-core/src/validate.rs:974`).
- Course `inputScript` (script names) and `speech.voices[role].prefer` (regex sources) are validated by `unknown_input_script` and `bad_voice_pattern` (`regex_problem` in `src/validate.rs` is a structural check, no regex engine in core).
- Speech validation: `bad_speech` covers rate outside 0.1..10, pitch outside 0..2, empty voice label or `match`, empty `speak.lines`, empty line text, and an empty item `speak` string. `unknown_voice` covers a line `voice` not in `speech.voices`, and any named voice when `speech.voices` is absent (`crates/dojo-core/src/validate.rs:398`).
- A stimulus `speak` is typed (`Speak`, `deny_unknown_fields`): non-conforming JSON is a parse error, not passed through. Item `speak` stays an opaque string.
- Placement: `course.placement.perUnit` is validated (`bad_placement` if < 1, in `check_course`) and defaults to 5 (`PlacementConfig`, `crates/dojo-core/src/content.rs:158`); `web/session.js:145` reads it for placement queues.
- Unit `placement: false` (`crates/dojo-core/src/content.rs:121`) is documented as excluding the unit from placement (`crates/dojo-core/src/schema.rs:71`); core only stores and validates it, it does not filter queues on it. `placement_unused` (warning, `crates/dojo-core/src/validate.rs:461`) fires for such a unit when `course.placement` is absent. `bad_placement` also fires when `course.placement` is set and no unit with `placement !== false` has active items.
- `applyPlacement` (`crates/dojo-core/src/srs.rs:285`): `known = false` returns the record unchanged (null stays null). A record whose stage is already >= min(4, max stage) is returned unchanged. Otherwise stage becomes that target, `last = now`, `ok`/`bad` default to 0 when absent, and an unseen item becomes a new record. `due = now + round(ladder[target] * (0.6 + 0.8 * r))`, where `r` is the top 53 bits of one splitmix64 step over `seed` divided by 2^53 (in `apply_placement`). Rust and `tools/reference/srs.js` must agree (vectors in `tests/vectors/srs.json`).
- Fold runs after case folding and before strip-punctuation, collapse and trim (`crates/dojo-core/src/check.rs:24`). Entry forms: single char -> any string (`""` deletes), or equal-length range `"A-Z"` -> `"a-z"` mapped char by char. First matching entry wins.
- `normalize` itself silently skips malformed fold entries; only the validator (`bad_fold`) and `api` reject them. `fold_too_large` fires for more than 256 entries or a single-char entry whose target exceeds 16 chars (counted in chars, not bytes).
- Empty `fold` leaves the text unchanged, so answers without fold keep their verdicts.
- `bad_plugin_path` is only the syntactic check (absolute, `\`-rooted, drive letter, or a `..` segment). Missing, outside-folder, symlink-escape and non-file checks are in `dojo-cli` (`validate_course`).
- Each of the 8 item structs carries an optional free-form `meta` (`serde_json::Value`, e.g. the `Item` structs in `src/content.rs`) and an optional `stimulus` id; core never reads `meta`. `deny_unknown_fields` on `Plugins` means unknown plugin keys are rejected.
- Course `normalize` is used only by the validator's duplicate-prompt and leak checks (`fold_norm`, `src/validate.rs`): the item's normalize object if its fold is non-empty, else the course's if its fold is non-empty, else the item's own. The browser engine instead uses `item.normalize || course.normalize` as a whole object (`web/session.js` `normalizeOpts`); change both together.
- `apply_answer` on a wrong answer drops `LEGACY_VECTOR_DROP` (2) stages but never below 1 for an item that was ever learned; `due = now + ladder[stage]`. `apply_answer_drop` allows configuring the drop.
- `apply_practice` on a correct answer to a started, not-yet-due record only bumps `ok` and `last`. `apply_practice_drop` allows configuring the drop.
- `drop_for_unit_json` resolves `dropOnWrong` with order: unit > course srsByType[itemType] > course srs > 1; always returns a value, `COURSE_DEFAULT_DROP` (1) when nothing is configured; values outside 0..=10 fall through to the next level. `LEGACY_VECTOR_DROP` (2) applies only when `applyAnswer`/`applyPractice` get no `drop` (`api.rs` `drop`, `:82`).
- Topic-level SRS (`srs.scope:"entity"`, `SrsScope` in `src/content.rs`): `srs::entity_view`, `srs::apply_entity` (`EntityMode` Answer/Practice/Relearn/Placement; returns `{memberId: record}` for every active member), `srs::pick_drill`; `groups::build_queue_scoped` (representative pass over `build_queue_with_groups`, `Scope{members,drill}`), `groups::group_counts_scoped` / `entity_stats_scoped`. WASM names: `entityView`, `applyEntity` (members `[{id,status?,retired?}]`, retired filtered in api), `buildQueue` + optional `scopedMembers`/`scopedDrill` (output gains `drills` only when `scopedMembers` is present), `groupCounts`/`entityStates` + optional `scopedEntities`. `unitConfig` also returns `scope` and `drill`. Validator codes `scope_by_type`, `bad_drill`, `mixed_entity_scope`. Tests: `tests/entity_scope.rs`, vectors `entityView`/`applyEntity` and scoped `buildQueue` cases.
- `unit_config` (`crates/dojo-core/src/srs.rs:95`) is the only course-level resolver for per-unit settings: `newPerDay` = unit `newPerDay` (>= 0) or null; `ladder` = `ladder_for_unit_json` with no item type; `dropOnWrong` = `drop_for_unit_json` with no item type; `newOrder` = unit > course > `file`; `dropByType` = one `drop_for_unit_json` per type in `srsByType`. Do not re-derive these rules elsewhere (JS, CLI).
- `weakest` ranks by `(bad+1)/(ok+bad+2)` plus 0.1 when stage < 3; default limit 10.
- Progress objects keep unknown fields (`preserve_order`, `float_roundtrip`); do not add typed fields that drop them.
- `examDraft` (top-level, one slot, no version field) is either an open draft (`sid`, `updatedAt`, payload) or a closed tombstone (`sid`, `updatedAt`, `closed`). Core checks only that `sid` is a string and `updatedAt` a number (`is_valid_draft`, `crates/dojo-core/src/progress.rs:334`); `closed` must be a string. Payload fields are opaque and kept byte-identical; `sanitize` does not touch them (test `draft_sanitize_keeps_draft_byte_identical` in `src/progress.rs`).
- `merge` of drafts is a join (commutative, associative, idempotent). Drafts with `updatedAt` below `max(resetAt)` of the two sides are dropped (checked only when that `resetAt` is non-zero). The slot is the greatest candidate under `draft_cmp`: `updatedAt`, then `sid` (UTF-16), then closed over open; among closed the reason (`expired` lowest), among open more `answers`, then stable JSON.
- `closedSids: [{sid, updatedAt}]` is an optional bookkeeping list inside the slot, sorted ascending, at most 32 entries (newest kept, `CLOSED_SIDS_MAX` `crates/dojo-core/src/progress.rs:371`), absent when empty. Each input list is first trimmed to 128 valid entries (largest `updatedAt`, ties: larger sid; `bound_closed_sids`, `crates/dojo-core/src/progress.rs:356`, `CLOSED_SIDS_BOUND` `:375`). A sid listed there is closed whatever the slot holds. The synthetic tombstones it produces use reason `expired`.
- If no candidate survives `resetAt` but a valid draft existed, the `examDraft` key is removed. With no valid draft on either side, the generic top-level merge applies. An invalid draft never beats a valid one.
- Item ids must match `^[a-z][a-z0-9]*-[0-9]+$` (`validate` rule, `crates/dojo-core/src/validate.rs:124` `is_valid_id`); course ids use `is_valid_course_id` (`^[a-z0-9][a-z0-9_-]{0,47}$`).
- Per-unit settings (`course.units[]`): `newPerDay` (`crates/dojo-core/src/content.rs:125`), `srs.ladder`, `placement` and `newOrder` (`crates/dojo-core/src/content.rs:131`; enum `NewOrder` at `:113`; order for new items: file or random). All are optional and absent means no change: `build_queue` with no caps is the old behaviour, and `content.json` serialization skips absent fields.
- `buildQueue` caps (`crates/dojo-core/src/srs.rs:221`): a fresh id is taken only while its unit's count is below `unitNewCaps[unit]` (the unit must be listed in both `unitNewCaps` and `itemUnits`; otherwise uncapped), and the global `newAllowance` still binds. Records that are not new do not count. A cap of 0 blocks the unit. Caps are counted over the items the queue takes, in `order`.
- `ladderForUnit` / `ladder_for_unit_json` (`crates/dojo-core/src/srs.rs:43`) work on the raw course JSON, so the WASM does not parse the whole course. Order: unit `srs.ladder`, then `srsByType[itemType].ladder` (only when `itemType` is given), then course `srs.ladder`, else `DEFAULT_LADDER`. A ladder counts only if it is a non-empty array of integers (`json_ladder`, `crates/dojo-core/src/srs.rs:35`); an empty or non-integer `srsByType` ladder falls through to the next step. An unknown unit falls through the same way. Drop resolution (`drop_for_unit_json`, `crates/dojo-core/src/srs.rs:72`): unit `srs.dropOnWrong`, then `srsByType[itemType].dropOnWrong`, then course `srs.dropOnWrong`, else 1.
- `bad_unit_settings` (`crates/dojo-core/src/validate.rs:453`-`:457`): negative `newPerDay`, or a unit `srs.ladder` that fails `ladder_problem` (`crates/dojo-core/src/validate.rs:164`; same rules as course `bad_ladder`: at least 2 entries, non-negative, first 0, non-decreasing). The `CODES` text for `bad_unit_settings` says "non-increasing"; the code enforces non-decreasing, and equal neighbours pass.
- Groups (`crates/dojo-core/src/groups.rs:1-9` module header): caps count ENTITIES; a cap never splits an entity (all items of an admitted entity go into fresh); units of a capped group are exempt from unit caps and the global allowance. `group_counts` ignores retired items.
- Adding an item type means a new `Item` variant, a `check` function and a `web/types/<name>.js` file.
- New content-quality warnings (all severity: warning): `foreign_script` (text contains letters from a script not in Latin/Cyrillic/Hiragana/Katakana/CJK; whitelist via `course.scripts`), `prompt_type_mismatch` (prompt asks to write/type but type has no text input, or asks to choose/pick on a gap), `ambiguous_answer` (`check_ambiguous_answer`, helper `has_slash_outside_brackets`; gap with several non-ASCII answers and no disambiguation hint like "any"/"one of"/digit/"любой"/"или", choice/multi option with '/' or '／' outside parentheses (ASCII `()` or full-width `（）`; a '/' inside parentheses is fine; nesting is handled; an unbalanced opener swallows the rest), or duplicate options after normalization; the warning advises to split into separate options or reword with "or"/"или"), `order_blanks_mismatch` (number of `___` blanks in prompt differs from number of steps in an order item).
